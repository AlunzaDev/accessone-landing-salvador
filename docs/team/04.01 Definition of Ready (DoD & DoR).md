# Definition of Ready y Definition of Done

Acuerdos cortos sobre cuándo una tarea puede empezar y cuándo puede ir a producción. Si una regla no se puede comprobar con una casilla, no es un acuerdo: se reescribe.

## Definition of Ready (DoR)

Una historia entra a sprint solo si cumple todo esto:

- [ ] Tiene issue publicado en GitHub (`estado: publicado` en el vault). Un borrador no existe para el equipo.
- [ ] Tiene objetivo y valor: "Como… quiero… para…".
- [ ] Tiene criterios de aceptación verificables en Dado / Cuando / Entonces.
- [ ] Si tiene interfaz, tiene diseño o prototipo aprobado.
- [ ] Si toca la API, el contrato está acordado (ver 02.02 API Contracts & Data Flow).
- [ ] Si toca datos o permisos, el catálogo de permisos y las reglas de negocio están confirmados (01.03 Reglas de Negocio).
- [ ] El equipo la estimó en refinamiento.
- [ ] No tiene dependencias externas sin resolver. Si depende de una app externa, su dueño confirmó.

Si falta algo, la historia se queda en refinamiento. No se "arranca y se aclara después".

## Definition of Done (DoD)

Una historia está terminada solo si cumple todo esto:

- [ ] Cumple todos sus criterios de aceptación.
- [ ] Tiene pruebas: unitarias en código nuevo; integración en flujos críticos (API, BD, 401/403); E2E para el proceso principal antes de producción.
- [ ] Un bug corregido incluye una prueba que falla antes del arreglo y pasa después.
- [ ] Checks en verde en local: `make check` en backend; `pnpm typecheck` y `pnpm lint` en frontend.
- [ ] PR con al menos una aprobación de otra persona. Nadie aprueba su propio PR.
- [ ] El PR tiene menos de 500 líneas de cambio efectivo. Si pasa, se divide.
- [ ] Si cambia la interfaz, el PR incluye captura.
- [ ] La documentación afectada está actualizada en el mismo PR: esta carpeta del vault, el README del repo o el ADR.
- [ ] Si hay deuda que queda, tiene issue con etiqueta `deuda`.

## Listo para producción

Una historia se puede desplegar solo si cumple el DoD y además:

- [ ] Pasó la revisión del Tech Lead si cambia contrato de API, datos, migraciones o permisos.
- [ ] Probada en staging, o en una restauración del respaldo si staging no existe (ver 03.02).
- [ ] Hay plan de rollback escrito para el cambio.
- [ ] Hay responsable disponible para revisar el despliegue después de publicar.
- [ ] Si cambia la identidad o los permisos que consumen las apps, las apps fueron avisadas (chatbot-parker, sikkounter, cotizapp).

## Qué se revisa en un PR

El revisor evalúa correctitud, casos borde, seguridad (validación, permisos, datos expuestos), legibilidad, pruebas e impacto en datos y migraciones. Los comentarios llevan prefijo:

| Prefijo       | Significado                  |
| ------------- | ---------------------------- |
| `bloqueante:` | Se corrige antes de fusionar |
| `sugerencia:` | Mejora opcional              |
| `pregunta:`   | Duda; no bloquea             |
| `nit:`        | Detalle menor de estilo      |
